1. One-line Idea

Most companies record support calls but nobody has time to listen to them. Call-Centre Radar listens, finds important moments, and shows managers exactly what needs action.

Main promise: every insight is backed by the exact timestamp and words spoken in the call.

For managers

Open one dashboard and see which calls need attention today.

For operations leaders

See trends, repeated complaints, unresolved issues, and agent workload.

For technical judges

Show a clear AI pipeline with transcription, evidence extraction, LLM analysis, validation, and caching.

Winning POC Strategy

The demo should not feel like a checklist of requirements. It should feel like a bank-grade product: every AI decision can be verified against the call, insights arrive quickly, and the manager gets a clear next action.

Trust

Every judgment has a timestamp, speaker, quote, and a Show Me Why path back to the recording.

Speed

The dashboard shows manager-ready results immediately from cached SQLite analysis and live job progress for new uploads.

Action

High-risk calls include a manager brief and recommended next action, clearly separated from evidence-backed facts.

Core difference: most simple demos stop at audio -> Whisper -> LLM -> dashboard. Our POC is audio -> transcript turns -> evidence -> validated AI judgment -> prioritized manager action.

4. Live Call Processing Flow

The sample calls are only seed data. The real product flow supports new audio files given during the demo.

Upload MP3 new call from judge
->
Create job queued status
->
Split audio agent left, customer right
->
Transcribe speaker + time
->
Analyze evidence + LLM
->
Show result dashboard updates
1

Upload or ingest

The user uploads a call recording and basic metadata such as customer name, agent name, and call start time.

2

Split channels

The dataset says left channel is the agent and right channel is the customer, so speaker separation is reliable for these files.

3

Transcribe both speakers

faster-whisper creates timestamped text for each channel. The app merges the turns into one conversation timeline.

4

Extract evidence first

A deterministic engine finds candidate moments for complaints, anger, resolution, escalation, fraud, repeat calls, and agent mistreatment.

5

Run LLM analysis

The local LLM receives the transcript plus evidence candidates and returns structured JSON only.

6

Validate and save

The validator rejects unsupported claims, missing timestamps, fake quotes, invalid scores, and summaries over 40 words.

7. AI Analysis Design

The solution should use an LLM, but the LLM should not be the only source of truth. The system first finds evidence, then asks the LLM to reason over that evidence, then validates the answer.

Evidence design rule: every AI judgment must reference immutable transcript_turn_id values. Timestamps and quotes are derived from stored transcript turns, not written freely by the LLM.
Transcript all speaker turns
->
Evidence engine rules + sentiment
->
Local LLM structured reasoning
->
Validator reject bad claims
->
Final analysis saved JSON

What the LLM produces

  • Customer intent
  • Mood at start and end
  • Mood shift timestamp
  • Resolution status
  • Summary under 40 words
  • Needs-attention score
  • Radar Priority score breakdown
  • Issue category
  • Manager brief
  • Recommended action
  • Customer journey summary
  • False-resolution flag
  • Repeated-question events
  • Silence and conversation-balance signals
  • Agent treatment score
  • Evidence for every judgment

What the validator checks

  • Output is valid JSON.
  • Score is between 0 and 100.
  • Summary has 40 words or fewer.
  • Every claim has timestamp and quote.
  • Quote exists in transcript.
  • Timestamp belongs to a real transcript turn ID.
  • Score factors link to supporting evidence.
  • Unsupported claims are rejected or marked uncertain.

POC Quality Signals

These are improvement signals from the shared chat that are valuable for the POC only if they remain evidence-backed. We should implement a small number well instead of many unreliable metrics.

Best POC signals

  • False resolution: agent says it is handled, but customer later asks what is still pending.
  • Repeated questions: same information requested multiple times, useful for coaching or process issues.
  • Long silence: audio has a meaningful silent gap, shown with a clickable timestamp.
  • Conversation balance: agent/customer talk ratio from the stereo channels.
  • Customer journey deterioration: repeat calls for same issue with worsening mood or unresolved outcomes.

POC rule

Only show a quality signal when the system has evidence from transcript turns or measurable audio timing.

Example: do not claim "agent interrupted customer" unless overlap or turn timing supports it.

8. Multi-LLM Strategy

For the demo, the default path should be free and local. The architecture should still allow faster, slower, stronger, or paid models later without changing the product.

Call transcript speaker and timestamps
->
Model router choose by speed, cost, risk
->

+
Accurate model slower or optional paid
->
Validator accept, retry, compare
Mode Purpose Cost When to use
Fast local LLM Quick live demo analysis. Free Short calls, low-risk calls, first-pass results.
Stronger local LLM Better reasoning, slower response. Free, but needs more hardware High-risk calls, unclear resolution, low confidence.
Two-model agreement Improve trust by comparing outputs. Free if both are local Manager attention score above a threshold.
Optional paid model Higher accuracy after hackathon. Paid, not required for demo Production mode, compliance review, difficult calls.
Design rule: every model must implement the same analyzer interface and return the same JSON schema. This keeps the system open for better models later without rewriting the dashboard or API.

9. Agent Treatment and Customer Satisfaction

A strong differentiator is tracking how service-care staff are treated on calls. This is useful for wellbeing, training, escalation, and management support. We should also estimate customer satisfaction for each service person so managers can see who is creating positive outcomes.

Detected behavior

  • Respectful or polite customer
  • Frustrated but respectful customer
  • Rude or insulting customer
  • Threatening language
  • Repeated interruptions
  • Personal blame toward the agent
  • Manager escalation request

Agent treatment metrics

  • Average treatment score
  • Difficult calls handled
  • Abusive calls today
  • Escalation-heavy calls
  • Calls needing supervisor support
  • Evidence clips for each flag

Customer satisfaction by service person

  • Estimated satisfaction score per agent from 0 to 100.
  • Signals: resolved outcome, final customer mood, positive closing words, repeat complaint, escalation, and call-back requirement.
  • Every score links to call evidence so it is not a black-box rating.
  • Use as coaching and support signal, not as the only performance measure.

12. Logging and Observability

We need to log enough to test, debug, and improve the product. The logs should tell us what happened, which model was used, how long each step took, and why a result was accepted or rejected.

What we log

  • Request ID, call ID, job ID, customer ID, and agent ID.
  • Job lifecycle: queued, audio split, transcribing, evidence extraction, LLM analysis, validation, complete, failed.
  • Duration for each step and total processing time.
  • Transcription model, LLM model, prompt version, rule version, and schema version.
  • Transcript turn IDs used by each AI judgment, score factor, quality signal, and Show Me Why link.
  • Radar Priority score breakdown, issue radar category, customer journey match, and manager brief version.
  • Audio timing events such as silence windows, channel balance, and evidence jump timestamp.
  • Validation failures such as missing evidence, fake quote, invalid JSON, or summary too long.
  • Manager actions: reviewed, escalated, dismissed, corrected, or reprocessed.

What we avoid logging

  • Do not print full raw audio content in logs.
  • Do not expose sensitive banking data in plain operational logs.
  • Keep model prompts and outputs in a controlled audit store, with redaction where needed.
  • Separate debug logs from business audit logs.

13. Testing and Accuracy Plan

Unit tests prove the code behaves correctly. Accuracy tests prove the AI product is useful. We need both.

100% unit test target

  • Target 100% unit test coverage for domain logic and service logic.
  • Cover scoring, validation, evidence matching, transcript merging, status transitions, API schema rules, and summary word-count rules.
  • Cover Radar Priority factor math, quality-signal detection, Issue Radar grouping, customer journey matching, and evidence jump URLs.
  • Use coverage gates in CI so new code cannot reduce coverage.
  • Exclude generated files, migrations, static assets, and test fixtures from the coverage percentage.
  • Keep integration and UI tests separate from unit test coverage.

Accuracy evaluation

  • Create a gold set of calls manually labeled by the team.
  • Measure transcription word error rate on a few manually checked calls.
  • Measure intent accuracy, resolution F1, mood-shift tolerance, and issue-category accuracy.
  • Measure false-resolution precision, repeated-question detection precision, silence-event timing tolerance, and conversation-balance correctness.
  • Measure evidence precision: does the quote really support the claim?
  • Measure evidence recall: did we find the important moments?
  • Track hallucination rate: claims without valid evidence must be zero after validation.
Quality area Metric Target for demo
Transcript Manual review plus word error rate on sample calls Good enough that evidence quotes are understandable.
Speaker attribution Correct agent/customer channel assignment Near 100% for stereo dataset because channel mapping is known.
Evidence grounding Claims with valid timestamp and matching quote 100% of displayed claims must have evidence.
Resolution detection Resolved/unresolved classification High precision for manager attention calls.
Attention queue Top risky calls include truly important calls Top 10 should feel obviously useful to a manager.
Radar Priority breakdown Score factors add up correctly and each factor has evidence 100% deterministic math correctness; evidence required for each displayed factor.
Issue Radar Issue grouping and trend direction against labeled sample calls Useful grouping with representative evidence for every shown issue.
Customer Journey Repeat issue and mood/outcome sequence accuracy Correct on prepared demo customers and regression-tested against gold cases.
Agent satisfaction score Correlation with final mood, resolution, and positive closing language Useful directional score, always evidence-backed.
Honest technical note: 100% unit test coverage does not mean 100% AI accuracy. The right answer is 100% coverage for deterministic code plus a separate AI evaluation suite with labeled calls and regression tracking.

15. SOLID Principles

SOLID keeps the code clean enough for senior technical reviewers and easier to extend after the hackathon.

Principle How we apply it
Single Responsibility Audio splitting, transcription, evidence extraction, LLM analysis, validation, scoring, and storage are separate services.
Open / Closed Add new evidence rules, new LLM provider, or new transcription engine without rewriting the whole pipeline.
Liskov Substitution Any transcriber implementation should return the same transcript interface, whether it uses faster-whisper or another engine.
Interface Segregation Small interfaces: Transcriber, Analyzer, EvidenceExtractor, Validator, Repository. No giant service object.
Dependency Inversion Business logic depends on interfaces, not directly on Ollama, ffmpeg, SQLite, or a specific model.

18. What Can Go Wrong?

A strong demo plan should not pretend everything is perfect. The system must show clear status, recover gracefully, and explain limits honestly.

Core fallback rule: if a step fails, the dashboard should still show what is known, what failed, and what the manager can do next.
What can go wrong Impact How we handle it in demo Production mitigation
Audio upload fails New call cannot enter the system. Show a clear error: unsupported file, too large, or missing metadata. Virus scan, file validation, resumable upload, object storage.
Audio is not stereo Cannot use left/right channel speaker separation. Mark speaker confidence as low and process as single-speaker transcript, or reject with a helpful message. Add diarization fallback for mono recordings.
ffmpeg is missing Audio cannot be split or converted. Startup health check warns before demo starts. Container image includes ffmpeg and CI checks it.
Transcription is slow Live demo waits too long. Use a short demo call, show progress, and keep preprocessed backup calls ready. Use GPU workers, queue concurrency, chunking, and model-size selection.
Transcription is inaccurate Analysis may be wrong because evidence text is wrong. Show audio player next to transcript so reviewers can verify evidence. Confidence scoring, reprocessing, better model, human review workflow.
Local LLM is slow or unavailable Detailed analysis may not finish. Show deterministic preliminary analysis and mark LLM refinement as pending. Dedicated inference service, retry queue, model health monitoring.
LLM returns invalid JSON API cannot safely store analysis. Validator rejects it and retries once with stricter prompt. Structured output mode, schema validation, eval tests, fallback model.
LLM gives unsupported claim False manager alert or wrong conclusion. Reject any claim without matching timestamp and transcript quote. Evidence validator, regression evals, confidence thresholds, human review.
Two models disagree Unclear intent, mood, or resolution state. Show the result as low confidence and prefer evidence-backed deterministic flags. Use arbitration rules, human review, and a stronger model for high-risk calls.
Accuracy score drops after a change A model, rule, or prompt update may regress quality. Do not use the changed version in demo unless evals pass. CI accuracy regression suite with gold calls and versioned prompts.
Summary is longer than 40 words Violates assignment requirement. Validator rejects and asks model to shorten, or uses a template summary. Automated schema and word-count tests.
Database write fails Processed result may be lost. Show failed job state and keep temporary output for retry. Transactions, backups, retry policy, observability.
Dashboard cannot reach backend UI appears broken. Show offline banner and retry button. Health checks, uptime monitoring, graceful error pages.
Tunnel fails during demo Remote URL may stop working. Run locally on the presenter machine and have screenshots/video backup. Deploy stable backend infrastructure behind HTTPS.
PII appears in transcript Privacy risk for banking-style data. Use sample/demo-safe audio and clearly mark PII redaction path. Presidio redaction, encryption, access control, audit logs.
Rule engine over-flags calls Too many false positives in manager queue. Show evidence and confidence, not just final score. Tune weights, collect manager feedback, calibrate thresholds.
Important issue is missed False negative: manager does not see a risky call. Allow manual search and show all unresolved/low-confidence calls. Evaluation dataset, recall-focused thresholds, periodic rule/model updates.

Demo safety plan

  • Use one short live-upload audio file to keep processing fast.
  • Prepare several already-processed calls for immediate dashboard walkthrough.
  • Run a startup health check for ffmpeg, Whisper model, Ollama, database, and frontend/backend connectivity.
  • Keep the local app open even if the public tunnel fails.
  • Have a backup screen recording of the live-upload flow.

How to explain failures

  • Be transparent: the app shows job status and error reasons.
  • Separate known facts from AI conclusions.
  • Show confidence and evidence for every important flag.
  • Use fallback analysis when LLM refinement is not ready.
  • Explain the production upgrade path without hiding hackathon constraints.

19. Pros and Cons

Pros

  • Free to run with open-source local models.
  • Supports live new audio uploads.
  • Evidence-backed, which directly matches assignment scoring.
  • Simple manager dashboard with clear action list.
  • Call Detail is a strong proof screen: manager brief, recommended action, score breakdown, evidence, and audio jump.
  • Radar Priority is explainable because each factor has points and transcript-turn evidence.
  • Issue Radar and Customer Journey make the product feel useful beyond one-call summaries.
  • Technically defensible hybrid architecture.
  • Works even if LLM is slow by showing preliminary rule-based analysis.
  • Can scale later by swapping SQLite for Postgres and local worker for queue workers.
  • Agent treatment tracking adds a strong human and business angle.

Cons and risks

  • Transcription is the slowest part of live processing.
  • Local LLM quality depends on laptop/server hardware and model choice.
  • Whisper errors can affect downstream analysis.
  • Rule engine needs tuning after reviewing real transcripts.
  • Fully free cloud hosting is not ideal for heavy AI inference.
  • Mono audio would require speaker diarization fallback.
  • Long calls may need chunking and progress updates.
  • More POC screens mean more demo preparation and more UI states to test.
  • False-resolution and repeated-question signals must be carefully tuned to avoid overclaiming.
  • Agent satisfaction scores are directional and must be positioned as coaching support, not a final performance judgment.
  • PII handling must be clear for banking-like conversations.

21. Questions We Can Answer in Demo

These are likely questions from technical and business reviewers, with short answers the team can use.

Question Answer
Can it process a new audio file live? Yes. Upload creates a job, then the worker transcribes, analyzes, validates, and updates the dashboard.
Why should we trust the AI output? The LLM must cite timestamped transcript evidence. The validator rejects unsupported claims.
What exactly is evidence? A saved transcript turn with immutable turn ID, speaker, timestamp, and quote, linked back to the audio.
Can the LLM invent timestamps or quotes? No. The LLM returns transcript turn references; timestamps and quotes are read from SQLite transcript turns.
What is the Show Me Why button? It opens the supporting transcript turn and jumps the audio player to the evidence timestamp.
Can the manager play the audio? Yes. The Call Detail screen has a full audio player with play/pause, speed control, jump back, and evidence timestamp jumps.
Can the transcript follow the audio? Yes. The planned UI highlights the active transcript turn while the recording plays.
What is Radar Priority? It is an explainable manager-attention score based on unresolved status, mood, repeat contact, risk, and evidence-backed quality signals.
How is Radar Priority calculated? Deterministic score factors add points, and each displayed factor must link to transcript or audio evidence.
Can managers see the score breakdown? Yes. The call detail screen shows every score factor, points added, and Show Me Why evidence link.
What is Manager Brief? A short manager-ready explanation of why the call matters and what risk or opportunity it contains.
Is Recommended Action treated as evidence? No. It is clearly labeled as a recommendation; facts and evidence remain separate.
Why not use only rules? Rules are fast and reliable for evidence, but LLM reasoning handles nuanced intent, mood, and resolution.
Why not use only LLM? Pure LLM is slower and more likely to hallucinate. Evidence-first analysis is safer.
Is it free? Yes for the hackathon path: local faster-whisper, local Ollama, SQLite, and open-source libraries.
What is the bottleneck? Transcription. Evidence extraction and scoring are quick after transcript generation.
Can we run multiple LLMs? Yes. The analyzer interface allows fast local, stronger local, two-model agreement, or optional paid models later.
Do we need a paid model for the hackathon demo? No. The demo path is local faster-whisper, local Ollama, SQLite, and open-source libraries.
What if the local LLM is slow? The app shows live processing status and can fall back to deterministic preliminary results or precomputed demo calls.
What if two models disagree? The result is marked low confidence and the product relies on evidence-backed deterministic signals first.
Can this scale? Yes. The services are modular: move DB to Postgres, audio to object storage, and workers to queue/GPU infrastructure.
Why SQLite for POC? It is free, simple, reliable for a laptop demo, and enough to persist transcripts, evidence, jobs, and analysis.
Can SQLite be replaced later? Yes. Repository interfaces keep business logic independent from the database implementation.
How do you identify speakers? The assignment audio is stereo: left is agent, right is customer. We split channels before transcription.
What if the demo audio is mono? The POC marks speaker confidence as low or uses a diarization fallback path if available.
Can it process a file we have never seen before? Yes. Upload creates a fresh processing job; preprocessing is done by the app, not by the presenter.
Do we preprocess audio manually? No. The app validates, converts, splits channels, transcribes, analyzes, and stores results automatically.
Can it protect sensitive data? Yes. Local processing avoids external APIs by default, and PII redaction can be added with Presidio.
What is the business value? Managers review the few calls that matter instead of randomly sampling hundreds of recordings.
What is Issue Radar? It groups recurring call issues into critical, emerging, and stable categories with trend direction and evidence examples.
Why Issue Radar instead of generic trends? Issue Radar is more action-oriented: it tells managers what operational problem needs attention now.
Can we track repeat caller experience? Yes. Customer Journey shows repeat issues, mood changes, outcomes, and follow-up risk over time.
Can we detect false resolution? For POC, yes when evidence shows the call sounded closed but later turns reveal pending work or customer confusion.
Can we detect repeated questions? Yes as an evidence-backed quality signal using repeated intent/info-request patterns in transcript turns.
Can we detect long silence? Yes. Silence is measured from audio timing and displayed only with a timestamped evidence window.
Can we measure agent/customer talk balance? Yes, especially for stereo audio, by calculating talk time per channel and showing a simple ratio.
Can we track how service people are treated? Yes. The app flags abusive, disrespectful, or high-stress moments with evidence and uses them for support/coaching.
Can we measure customer satisfaction by agent? Yes as an estimated, evidence-backed directional score based on outcome, final mood, positive closing language, and repeat contact.
How do we avoid unfair agent scoring? Scores are positioned as coaching signals, include evidence, and should not be used as the only performance measure.
How do we test accuracy? Use manually labeled gold calls and measure transcript quality, intent, mood, resolution, evidence precision, and signal precision.
Does 100% unit coverage mean 100% AI accuracy? No. Unit coverage proves deterministic code; AI accuracy needs a separate labeled evaluation suite.
How do we debug wrong results? Logs include request IDs, job IDs, model versions, prompt versions, validation results, score factors, and evidence turn IDs.
What happens if evidence is missing? The claim is rejected, hidden, or marked uncertain instead of being shown as a fact.
What charts are worth building for POC? Mood timeline, Radar Priority breakdown, Issue Radar grouping, Customer Journey timeline, and simple agent satisfaction/treatment bars.
Why avoid complex radar charts? They look decorative but add less demo value than evidence, audio sync, score breakdown, and manager actions.
Where can we host it for free? Frontend can use Vercel or Netlify free tier; heavy AI should run locally for the demo because free cloud inference is limited.
What if hosting or tunnel fails? Run the app locally, keep processed calls ready, and use a backup screen recording for the live-upload flow.
What is the strongest demo moment? Open a high-risk call, read the manager brief, click Show Me Why, and jump the audio to the exact evidence.
What can be built first if time is short? Call Detail, synced audio/transcript, evidence-backed intent/mood/resolution, Radar Priority breakdown, and dashboard ranking.

22. Final Recommendation

Build a hybrid, evidence-first call intelligence product: faster-whisper transcription + deterministic evidence engine + local/multi-LLM analysis + strict validator + SQLite + logs + accuracy evals + manager dashboard.

This gives the best balance for the hackathon: simple for managers, impressive for executives, defensible for architects, free to run, and capable of processing a new call during the demo.

The call detail screen should be the proof: Manager Brief, Recommended Action, Radar Priority breakdown, transcript evidence, and audio jump-to-timestamp. Issue Radar and Customer Journey are high-value extensions if the core flow is already solid.
